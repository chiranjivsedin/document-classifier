What We Built — v1 Current State

Fully operational, running locally

v1 is a fully working document classification pipeline. It accepts PDF, PNG, and JPEG files via a REST API, extracts text (using PyMuPDF for digital PDFs or RapidOCR for scanned/image documents), and classifies the document using a local Gemma language model running via Ollama — no cloud, no external API calls.

Pipeline Flow

  • Upload document (PDF / PNG / JPEG)
  • Route: text PDF or scanned image?
  • OCR if scanned (RapidOCR, ONNX)
  • Classify via Gemma 3 (4B, local)
  • Return category + confidence + reason

Tech Stack

  • Backend: FastAPI + Python 3.12
  • Model: gemma3:4b via Ollama
  • OCR: RapidOCR (ONNX runtime)
  • Frontend: React 19 + Vite + Tailwind
  • Fully self-hosted, no cloud dependency

The Problem with v1 — Why It Is Not Enough

Prompt engineering is not fine-tuning
🚨
Key Finding The current approach is prompt engineering — asking a general-purpose language model to guess a category by reading a prompt. This is not Supervised Fine-Tuning (SFT) and will not perform reliably in production.

Here is the difference between what v1 does and what it should do:

Aspect v1 — Prompt Engineering v2 — Supervised Fine-Tuning
How it works Writes a prompt asking Gemma to classify. Gemma generates a text answer. A model trained on labeled examples learns to classify directly.
Deterministic? No — same document can yield different answers Yes — same input always gives same output
Accuracy Moderate. Sensitive to prompt wording. High. Learned from real examples.
Speed 200–500ms (generates tokens one by one) <100ms (single forward pass)
Labeled data needed? No (why we used it for v1) Yes (50–100 examples per category)
Model size 2.5 GB (Gemma 4B) 65 MB (DistilBERT)

Model Selection — Why DistilBERT for v2

Choosing the right tool for the classification task

There are two families of models relevant to this task: generative (decoder) models like Gemma, and encoder models like BERT/DistilBERT. They are architecturally different and designed for different jobs.

How BERT Works — and Why It Suits Classification

BERT (Bidirectional Encoder Representations from Transformers) was created by Google in 2018. Unlike Gemma, BERT does not generate text. Instead, it reads an entire document simultaneously from both directions (left-to-right and right-to-left) and produces a rich numerical representation — a vector — that captures the meaning of the document.

Think of it this way:

Gemma (Generative / Decoder)

  • Reads document word by word, left to right
  • Predicts the next word at each step
  • "What word comes next?" is its core task
  • Produces text output (writes an answer)
  • Classification is forced — it must write "invoice"

BERT (Encoder)

  • Reads the entire document at once
  • Understands context from both directions
  • "What does this mean?" is its core task
  • Produces a vector (a compressed understanding)
  • Classification is natural — vector → label

The Classification Head: After BERT produces a document vector, a small linear layer (called a classification head) is added on top. This layer is trained to map the vector to one of our categories (invoice, contract, etc.). During fine-tuning, both BERT and this head are trained together on our labeled examples. The result: a model that has learned to recognize the specific language patterns of each document type in our dataset — not general knowledge, but task-specific knowledge.

DistilBERT is a compressed version of BERT — 40% smaller, 60% faster, retains 97% of BERT's accuracy. It is the standard choice when compute is a constraint.

💡
Why Not Just Fine-Tune Gemma? You can fine-tune Gemma for classification — but it's like using a truck to deliver a letter. Gemma has 4 billion parameters designed for open-ended text generation. DistilBERT has 66 million parameters designed exactly for understanding and classifying text. Fine-tuned DistilBERT on 500 labeled examples will outperform Gemma zero-shot, run 5× faster, use 40× less memory, and be fully deterministic.
Model Type Size Speed (CPU) Good For Our Use
gemma3:4b Generative LLM 2.5 GB 200–500ms Text generation, reasoning v1 only
gemma3:1b Generative LLM 700 MB 100–200ms Lightweight generation Not recommended
distilbert-base-uncased Encoder 65 MB <100ms Text classification (SFT) v2 target
bert-base-uncased Encoder 440 MB ~150ms Classification (heavier) Alternative
✅
Decision Keep gemma3:4b for v1 (it works today, no labeled data needed). Replace with fine-tuned distilbert-base-uncased for v2. The existing codebase is already designed for this swap — it takes one new file and one environment variable change.

Types of Fine-Tuning — What We Are Targeting

SFT is the correct approach for document classification
Approach Description Labeled Data? Accuracy Status
Prompt Engineering Craft a prompt telling the model what to do. No weight changes. No Moderate v1 (current)
Supervised Fine-Tuning (SFT) Train on labeled (document → category) examples. Weights update. Yes High v2 target
LoRA / PEFT Efficient SFT — train small adapter layers only, not full model. Yes High Alternative for v2
RLHF Human raters rank outputs; reward model trained on rankings. Yes (rankings) Very High Overkill for classification
📌
SFT for Classification (Plain English) We give the model hundreds of examples: "this document is an invoice", "this document is a contract", etc. The model's weights are updated so it learns the patterns specific to BPCL's document types — not general knowledge, but task-specific knowledge.

One Input Needed — Document Taxonomy

The technical architecture is ready; the category list is the final dependency

The current v1 system uses 7 placeholder categories: invoice, contract, id_proof, report, purchase_order, shipping_order, other. These were defined as starting assumptions during initial design and have not been validated against BPCL's actual document landscape.

⚠️
Why This Matters Supervised Fine-Tuning produces a model trained on a fixed set of categories. If we train on 7 assumed categories and BPCL's actual document types turn out to be different or more numerous, the model would need to be rebuilt from scratch — discarding all labeling and training effort. Getting the category list right upfront saves significant rework.

The technical side is fully decided and ready to build. The one remaining input is the confirmed list of document types that BPCL handles — this is domain knowledge that exists within the organisation and defines the scope of the classifier.

✅ We Are Ready to Begin — One Input Required

The architecture is finalised: fine-tuned DistilBERT, fully self-hosted, CPU-friendly, <100ms inference, drop-in replacement for the existing pipeline. To begin building the training dataset, we need:

The confirmed list of document types / categories that BPCL uses in its operations. This defines the label set for the training data and the final classifier output.

Recommended Path Forward

From v1 prompt engineering to v2 supervised fine-tuning
  • ✓

    v1 — Working Classifier Done

    Gemma 3 (4B) zero-shot classifier via Ollama. Full pipeline: upload → OCR if needed → classify → return result. React frontend with drag-and-drop UI. Fully local, no cloud.

  • !

    Confirm Document Taxonomy Blocked — needs input

    Get the confirmed list of BPCL document types from domain experts. This is the foundation of the entire fine-tuning effort — everything downstream depends on it.

  • 3

    Build Labeled Dataset

    Collect 50–100 sample documents per category (public sources, synthetic PDFs, or real documents). Label each with its category. Target: 300–500 total examples minimum.

  • 4

    Fine-Tune DistilBERT (SFT)

    Train distilbert-base-uncased on the labeled dataset using HuggingFace Trainer API. Evaluate on a held-out test set. Target: >85% F1 per category before shipping.

  • 5

    Evaluate & Iterate

    Track per-class F1 score, overall accuracy, and confusion matrix. Identify weak categories, add more labeled examples for those, retrain. Repeat until target accuracy is met.

  • 6

    Swap Into Pipeline (v2 live)

    Add services/classifier_finetuned.py implementing the same Classifier protocol. Switch via CLASSIFIER_BACKEND=distilbert environment variable. No other code changes needed.
